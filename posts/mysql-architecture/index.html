MySQL 架构详解

Categories: Database 2023-11-23

MySQL 是最流行的关系型数据库之一。理解其架构有助于我们更好地优化查询性能和排查问题。

MySQL 架构概览

MySQL 分为客户端和服务端两部分：

  • 客户端（mysql）：使用 mysql-connector 库可以在编程语言中使用 SQL
  • 服务端（mysqld）：包含连接层、服务层、存储引擎层

连接层

主要职责

连接层负责客户端连接请求的监听与建立，还包括：

  • 安全权限认证
  • 连接管理
  • 线程管理

连接管理

最大连接数：由参数 max_connections 控制。当达到最大连接数时，新的连接请求会被拒绝。

自动断开：wait_timeout 参数控制客户端连接自动断开的时间（秒）。

线程管理

线程管理分为两种模式：

  1. 每个连接一个线程：传统模式，每个客户端连接对应一个独立线程
  2. 线程池模式：固定数量的线程处理客户端请求，避免线程频繁创建、切换、销毁的开销

线程模式由参数 thread_handling 控制，支持在线修改。

服务层

服务层是 MySQL 的核心，负责 SQL 的解析、优化和执行。

查询缓存（Query Cache）

工作原理：

Query Cache 是一个内存中的键值存储：

  • Key：执行过的 SQL 语句
  • Value：查询的结果

执行一个 SQL 之前先检查是否命中查询缓存：

  • 如果命中，直接返回缓存结果
  • 如果未命中，执行完成后将查询结果缓存起来

失效问题：

Query Cache 失效非常频繁，只要对一个表进行更新操作，就会导致该表上的所有 Query Cache 失效。

注意：MySQL 8.0 已经移除了 Query Cache 功能，因为在大多数场景下它的效率并不高。

SQL 解析器（Parser）

Parser 负责对 SQL 语句进行词法分析和语法分析。

词法分析：将 SQL 中的字符串识别为数据库中的结构（表名、列名、关键字等）。

语法分析：检查该 SQL 是否符合语法要求，生成语法树。

例如：

SQL
SELECT name FROM users WHERE id = 1;

词法分析后识别出：

  • SELECT：关键字
  • name：列名
  • FROM：关键字
  • users：表名
  • WHERE：关键字
  • id：列名
  • =：运算符
  • 1：字面量

优化器（Optimizer）

Optimizer 负责生成执行计划，交给执行器执行。优化器会进行以下优化：

索引选择：当一个表有多个索引时，选择走哪个索引。

Join 类型选择：

  • Hash Join
  • Merge Join
  • Nested Loop Join

Join 顺序优化：决定多表连接的顺序，不同的顺序可能导致性能差异巨大。

谓词下推：将过滤条件尽可能地下推到存储引擎层执行。

可以使用 EXPLAIN 命令查看执行计划：

SQL
EXPLAIN SELECT * FROM users WHERE age > 18;

执行器（Executor）

根据执行计划执行语句。执行流程：

  1. 权限检查：判断该用户是否对查询的表有查询权限

    • 没有权限：返回权限错误
    • 有权限：打开表进行查询

  2. 调用存储引擎接口：执行器调用存储引擎的接口获取数据

  3. 返回结果：将查询结果返回给客户端

执行器分为两种情况：

无索引查询：全表扫描，逐行读取数据并判断条件。

走索引查询：通过索引快速定位到符合条件的数据。

存储引擎层

存储引擎层负责数据的存储和提取。MySQL 采用插件式的存储引擎架构，支持多种存储引擎。

Buffer Pool

作用：在内存中缓存表的数据页和索引页，加快访问速度。

大小控制：由参数 innodb_buffer_pool_size 控制。

淘汰策略：当 Buffer Pool 放不下所有的数据页时，使用淘汰算法（LRU 等）替换一些页。

Buffer Pool 是 InnoDB 性能的关键，通常建议设置为服务器内存的 50%-75%。

Log Buffer

作用：缓存事务的 Redo Log，保证事务的持久性。

刷盘策略：在 FORCE 模式下，需要在事务提交时将事务的 log 刷新到磁盘上持久化。

参数控制：

  • innodb_log_buffer_size：Log Buffer 的大小
  • innodb_flush_log_at_trx_commit：控制刷盘策略
    • 0：每秒刷盘一次
    • 1：每次事务提交时刷盘（最安全，性能较低）
    • 2：每次事务提交时写入文件系统缓存，每秒刷盘一次

自适应哈希索引（Adaptive Hash Index）

作用：加速索引的查询速度。

工作原理：InnoDB 根据查询频率和模式自动建立哈希索引，根据哈希索引快速（O(1) 时间）定位到数据位置，比查询 B+ 树快。

自动管理：无需手动创建，InnoDB 会自动根据访问模式创建和维护。

物理文件

MySQL 的物理文件分为以下几类：

数据文件

存储表的实际数据。在 InnoDB 中：

  • 共享表空间模式：所有表的数据存储在 ibdata1 文件中
  • 独立表空间模式：每个表有自己的 .ibd 文件

索引文件

存储索引数据。InnoDB 使用聚簇索引，索引和数据存储在一起。

日志文件

Redo Log：用于崩溃恢复，保证事务的持久性。由两个或多个固定大小的日志段组成，循环写入。

Undo Log：用于事务回滚和 MVCC（多版本并发控制）。

Binlog：二进制日志，记录所有修改数据库的操作，用于主从复制和数据恢复。

临时文件

查询过程中产生的中间结果，例如：

  • 临时表
  • 排序后的结果
  • Group By 的中间结果

页的组织

数据文件、索引文件和临时文件都是由一个或多个固定大小的页组成，页大小一般为 16KB。

这是 InnoDB 存储引擎读写数据的最小单位。

SQL 执行流程总结

一条 SQL 语句的完整执行流程：

客户端
  ↓
连接层（建立连接、权限认证）
  ↓
查询缓存（MySQL 8.0 已移除）
  ↓
解析器（词法分析、语法分析）
  ↓
优化器（生成执行计划）
  ↓
执行器（调用存储引擎接口）
  ↓
存储引擎层（读取/写入数据）
  ↓
返回结果给客户端

性能优化建议

Buffer Pool 优化

  • 合理设置 innodb_buffer_pool_size，通常为服务器内存的 50%-75%
  • 监控 Buffer Pool 的命中率

日志优化

  • 根据业务需求调整 innodb_flush_log_at_trx_commit
    • 高一致性要求：设置为 1
    • 可容忍少量数据丢失：设置为 2

连接优化

  • 合理设置 max_connections
  • 使用连接池减少连接创建开销
  • 调整 wait_timeout 避免空闲连接占用资源

查询优化

  • 合理使用索引
  • 避免全表扫描
  • 使用 EXPLAIN 分析执行计划
  • 优化 JOIN 查询的顺序

总结

理解 MySQL 的架构有助于我们：

  • 更好地优化查询性能
  • 排查数据库问题
  • 合理配置数据库参数
  • 设计高效的数据库应用

MySQL 的分层架构使得各层职责清晰，便于维护和优化。掌握每一层的工作原理是成为数据库专家的必经之路。
