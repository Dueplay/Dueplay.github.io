数据库隔离级别详解

Categories: Database 2023-11-16

数据库隔离级别是并发控制的核心概念，不同的隔离级别通过不同的加锁策略来平衡并发性能和数据一致性。

1. READ UNCOMMITTED（读未提交）

特点

READ_UNCOMMITTED 允许一个事务在另一个事务未提交的数据上执行读取操作，甚至在其他事务正在对这些数据进行修改的情况下也是可以的。

加锁机制

  • 事务不会对读取的数据应用共享锁（S 锁）、排他锁（X 锁）或范围锁（IS 锁、IX 锁等）
  • 事务只能获得 IX、X 锁，并且只能在 growing 阶段获得

为什么不需要锁

共享锁（S 锁）：在其他隔离级别中，读取操作可能会对数据应用共享锁，以防止其他事务修改这些数据。但在 READ_UNCOMMITTED 下，由于不关心其他事务的提交状态，甚至其他事务在写也可以读，所以不需要对读取的数据应用共享锁。

范围锁（IS 锁、IX 锁等）：这些锁通常用于保护一定范围的数据，以防止其他事务在该范围内进行修改。在 READ_UNCOMMITTED 下，不需要对读取的数据应用范围锁。

隔离性

READ_UNCOMMITTED 隔离级别提供了最低的隔离水平，因此在读取数据时不会强制要求对数据进行锁定。这使得在该隔离级别下可以更自由地读取数据，但也增加了数据一致性和事务安全性的风险。

可能出现的问题

  • 脏读（Dirty Read）：可以读取未提交的数据
  • 不可重复读（Non-repeatable Read）：同一事务中多次读取同一数据可能得到不同结果
  • 幻读（Phantom Read）：同一事务中多次查询可能看到不同的行数

2. READ COMMITTED（读已提交）

特点

事务只能读取已经提交的数据。这是大多数数据库系统的默认隔离级别（如 Oracle、PostgreSQL）。

加锁机制

在 READ_COMMITTED 隔离级别下，事务需要获得共享锁（S锁）或排他锁（X锁），具体的锁取决于对数据的读写操作。

加锁规则：

  • Growing 阶段：允许获取所有类型的锁
  • Shrinking 阶段：只允许获取 IS、S 锁

特性

在 READ_COMMITTED 隔离级别中，虽然共享锁可以防止其他事务在读取数据的同时对其进行修改，但由于事务只能看到已提交的数据，因此在事务之间仍然存在一些并发问题。

可能出现的问题

  • 脏读：✅ 已解决
  • 不可重复读：❌ 仍可能出现
  • 幻读：❌ 仍可能出现

性能

READ_COMMITTED 是相对较低的隔离级别，可以提供较好的并发性能，但在一些特定场景下可能会出现一些并发问题。

3. REPEATABLE READ（可重复读）

特点

使用 REPEATABLE_READ 隔离级别的一个目标是确保事务在其生命周期内可以多次读取相同的数据而不受其他事务的干扰。这是 MySQL 的默认隔离级别。

加锁机制

通过获取共享锁或排他锁，REPEATABLE_READ 隔离级别保证了在事务执行期间，数据的一致性和可重复性。

加锁规则：

  • Growing 阶段：允许获取所有类型的锁
  • Shrinking 阶段：不允许获取任何锁

这意味着一旦事务开始释放锁（进入 Shrinking 阶段），就不能再获取新的锁。

特性

REPEATABLE_READ 隔离级别通过持有读锁直到事务结束，确保同一事务中多次读取相同数据时，数据保持一致。

可能出现的问题

  • 脏读：✅ 已解决
  • 不可重复读：✅ 已解决
  • 幻读：❌ 可能出现（但 MySQL InnoDB 通过 Next-Key Lock 解决了幻读）

MySQL 的实现

MySQL InnoDB 引擎使用 Next-Key Lock（行锁 + 间隙锁） 来防止幻读：

  • 行锁：锁定具体的行
  • 间隙锁：锁定索引记录之间的间隙，防止其他事务插入数据

4. SERIALIZABLE（串行化）

特点

最高的隔离级别，强制事务串行执行，完全避免并发问题。

加锁机制

  • 读操作加共享锁，写操作加排他锁
  • 所有锁持有到事务结束
  • 可能对整个范围加锁

可能出现的问题

  • 脏读：✅ 已解决
  • 不可重复读：✅ 已解决
  • 幻读：✅ 已解决

性能

由于事务需要串行执行，并发性能最差，适用于对数据一致性要求极高的场景。

隔离级别对比

隔离级别脏读不可重复读幻读并发性能
READ UNCOMMITTED❌❌❌最高
READ COMMITTED✅❌❌较高
REPEATABLE READ✅✅❌*一般
SERIALIZABLE✅✅✅最低

*注：MySQL InnoDB 的 REPEATABLE READ 通过 Next-Key Lock 解决了幻读问题

两阶段锁协议（2PL）

数据库通过两阶段锁协议（Two-Phase Locking, 2PL）来实现不同的隔离级别：

Growing Phase（增长阶段）

  • 事务可以获取锁
  • 不能释放锁

Shrinking Phase（收缩阶段）

  • 事务可以释放锁
  • 不能获取新锁

不同隔离级别对 2PL 的限制：

READ UNCOMMITTED：

  • Growing: 可获取 IX, X
  • Shrinking: 不允许获取锁

READ COMMITTED：

  • Growing: 可获取所有锁
  • Shrinking: 只能获取 IS, S

REPEATABLE READ：

  • Growing: 可获取所有锁
  • Shrinking: 不允许获取锁

SERIALIZABLE：

  • Growing: 可获取所有锁
  • Shrinking: 不允许获取锁
  • 所有锁持有到事务结束

如何选择隔离级别

READ UNCOMMITTED

  • 适用场景：对数据一致性要求不高，追求极致性能
  • 典型应用：日志收集、监控数据

READ COMMITTED

  • 适用场景：大多数 OLTP 应用
  • 典型应用：电商系统、社交应用

REPEATABLE READ

  • 适用场景：需要事务内数据一致性
  • 典型应用：金融系统、账务系统（MySQL 默认）

SERIALIZABLE

  • 适用场景：对数据一致性要求极高
  • 典型应用：银行转账、库存扣减的关键操作

总结

隔离级别是在数据一致性和并发性能之间的权衡：

  • 隔离级别越高，数据一致性越好，但并发性能越差
  • 隔离级别越低，并发性能越好，但可能出现数据不一致
  • 大多数应用使用 READ COMMITTED 或 REPEATABLE READ
  • 根据具体业务需求选择合适的隔离级别
